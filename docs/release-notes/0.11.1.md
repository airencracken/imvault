# Imvault 0.11.1

Refines member invitations and closes gaps in invitation authorization.

Administrators can grant a member invitation access under **Admin → Users →
Allow invites**. The account shows a **can invite** badge, and **Invitations**
appears in the member's navigation on their next request. This permission is
separate from their role. Members create, list and revoke only their own codes;
new accounts do not inherit invitation access.

- Ordinary form submissions retain the full page and navigation. Validation
  preserves entered values, and one-time codes and links are served without
  caching.
- Revocation uses the shared confirmation dialog, including cancel behavior.
- The invitation page reflects the actual registration policy and explains how
  administrators can grant members access.
- Creating and revoking codes rechecks the issuer's current permission in the
  database, including whether their account is disabled.
- Codes from disabled issuers cannot admit new accounts until the issuer is
  enabled again. Removing invitation permission alone leaves previously issued
  codes active; administrators can revoke those separately.
- Provider signups now retain the invitation's issuer and code attribution,
  as password signups already did. Registration and code consumption remain
  one transaction.
- Malformed or duplicate permission values are rejected without changing access.

No schema or dependency changes from 0.11.0. Existing invitation permissions
remain in place. Back up your data using your usual procedure before upgrading.

Validation covers the full race suite, browser interactions, invitation use
limits, concurrent redemption, database constraints, CSRF and unauthorized
requests, provider attribution, and deliberate permission mutations. The release
also passes the amd64 and arm64 package lifecycle gates.

See [Accounts and invitations](https://github.com/airencracken/imvault/blob/v0.11.1/docs/accounts.md#invitations)
for setup and permission behavior.
